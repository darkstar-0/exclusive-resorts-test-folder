# Inquiry Form API Collection — README

## What this covers

Postman/Newman collection exercising `POST {{baseUrl}}/submit-form/`, the
backend endpoint the `/inquire/` form on `public-site.stage.exclusiveresorts.com`
posts to. Built from a real captured request (via Playwright route
interception during UI test development), covering the 8 scenarios below.

| ID | Scenario | Expected |
|----|----------|----------|
| API-01 | POST with all valid fields | 2xx, success payload |
| API-02 | POST missing a required field (Email) | 4xx with field-level error |
| API-03 | POST with malformed email | 4xx validation error |
| API-04 | POST without consent flag (`termsAgreement=false`) | 4xx — server-side enforcement |
| API-05 | POST with SQL-injection payload in FirstName | Sanitized; no DB error leaked |
| API-06 | GET on the submit endpoint | 405 Method Not Allowed |
| API-07 | Response time p95 over 10 calls | All < 2000ms |
| API-08 | Response shape matches contract | Required keys present, correct types |

## ⚠️ Live run result: blocked at the CDN layer (CloudFront 403)

**Every request capture used to build this collection came from Playwright's
`page.route()` interception, which stubs the response before it ever reaches
the real server.** We had high confidence in the *request* shape (field
names, encoding, the `values`/`form` envelope) because that's exactly what a
real browser sent — but the real response was never observed until this run.

**What I tried:** ran the full collection against real staging
(`https://public-site.stage.exclusiveresorts.com`) via `newman run
collection.json -e environment.json`.

**What I observed:** every single request in the collection — including the
plain baseline POST (API-01) and the unauthenticated GET (API-06) — returned
**HTTP 403** with an AWS CloudFront error page:

```
403 ERROR
The request could not be satisfied.
Request blocked. We can't connect to the server for this app or website at
this time. There might be too much traffic or a configuration error...
Generated by cloudfront (CloudFront)
Request ID: 0IwrnvLdl7zk9KLQRzbepfF9frV3z5cf4gdBVAXVRULuiWTGxjGlDg==
```

This response comes from CloudFront itself, not the application — the
request never reached the origin server or app logic. Because the block is
identical across every scenario, including a bare GET that carries no
form data and no session state, this rules out CSRF/session-token
enforcement (which would only affect state-changing requests) and points to
CDN-level filtering — most likely a WAF rule or bot-detection heuristic
keying off Postman/Newman's default request signature (User-Agent, missing
browser-standard headers like `Referer`/`Origin`, absence of a JS
challenge-solve, etc.) rather than anything about the request content.

**What this means for the assertions below:** none of the response-shape or
status-code expectations in this collection (API-01, API-02, API-08, and by
extension the negative-case expectations for API-03/04/05) have been
confirmed against a live response — every run so far returns the same
CloudFront 403 page regardless of what's actually in the request body. They
remain best-effort inferences from the request-capture work, marked
`ADJUST AFTER LIVE RUN` in the test scripts, until the CDN block is lifted
for testing.

**What I'd do in a real engagement:**
1. Ask the DevOps/platform team for a staging bypass — an IP allowlist entry
   for the testing machine/CI runner, or a CloudFront WAF rule exception for
   a known automation User-Agent.
2. If that's not available quickly, fall back to Playwright's
   `APIRequestContext` instead of a bare Postman/Newman call — it can reuse
   the real browser page's session, cookies, and headers, which may be
   enough to get past CDN-level bot filtering that a cold HTTP client can't.
3. Re-run this exact collection once access is granted, and replace every
   `ADJUST AFTER LIVE RUN` assertion with the real observed shape/status.

## Files

- `collection.json` — the Postman collection (import into Postman, or run via Newman).
- `environment.json` — `baseUrl` and `perfIterations`, placeholder values, no secrets.
  - Currently set to staging (`https://public-site.stage.exclusiveresorts.com`).
  - To point at production, edit `baseUrl` in this file to the real prod host —
    the actual production domain wasn't confirmed during UI testing (only
    staging was exercised), so don't assume the obvious `public-site.exclusiveresorts.com`
    without checking.

## Running it

Install Newman once:
```
npm install -g newman
```

Run the full collection (all scenarios once):
```
newman run collection.json -e environment.json
```

Run just the performance scenario (API-07) 10 times, isolated from the rest,
so the p95 calculation gets a real 10-sample window:
```
newman run collection.json -e environment.json --folder "API-07 - Response Time (p95)" -n 10
```
